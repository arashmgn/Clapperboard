CQRS چیست؟

جدا کردن مسیر خواندن از مسیر نوشتن — و اینکه چرا این جدایی دقیقاً همان مشکلاتی را حل می‌کند که در بازبینی این پروژه پیدا شدند.

01ایده‌ی اصلی

CQRS مخفف Command Query Responsibility Segregation است: یعنی مسیر «نوشتن» (Command) از مسیر «خواندن» (Query) جدا می‌شود، به‌جای اینکه یک کلاس یا متد مشترک هر دو کار را انجام دهد.

الان توی MovieController یک IMovieRepository داری که هم GetAllAsync/GetByIdAsync (خواندن) را دارد هم AddAsync/UpdateAsync/DeleteAsync (نوشتن) را، و کنترلر مستقیم صدایش می‌زند:

Controller→Repository (Read + Write)→DbContext

وضعیت فعلی — یک مسیر مشترک برای هر دو نوع عملیات

Command→CommandHandler→DbContext
Query→QueryHandler→DbContext

با CQRS — هر عملیات (نه هر Entity، هر عملیات) کلاس مستقل خودش را دارد

02اجزای CQRS

هر عملیات یک شیء ساده‌ی حامل داده می‌گیرد، به‌علاوه یک Handler که منطق واقعی — همان کاری که الان داخل بدنه‌ی اکشن کنترلر است — را انجام می‌دهد.

Command · Write

تغییر state

فقط داده‌ی لازم برای ایجاد/ویرایش/حذف را حمل می‌کند. نتیجه‌اش معمولاً همان چیزیست که ساخته شد، نه یک لیست.

public record CreateMovieCommand(
    string Title,
    string ImdbId,
    DateTime ReleaseDate,
    List<int> GenreIds
);
Query · Read

خواندن بدون عارضه

فقط داده‌ی لازم برای فیلتر/شناسایی رکورد را حمل می‌کند. هیچ‌وقت داده را تغییر نمی‌دهد.

public record GetMovieByIdQuery(
    int Id
);

Handler — جایی که منطق واقعی زندگی می‌کند

کنترلر لاغر می‌شود و فقط dispatch می‌کند؛ چک کردن ژانرها، ساختن Movie، صدا زدن AddAsync، map کردن به Dto — همه می‌روند این‌جا:

public class CreateMovieCommandHandler
{
    // دقیقاً همون کاری که الان توی
    // MovieController.Create انجام می‌شه
    public async Task<MovieDto> Handle(CreateMovieCommand command) { ... }
}

03چرا مشکلات همین پروژه را حل می‌کند

  • try/catch تکراری در هر اکشن — منطق می‌رود توی Handler، و مدیریت خطا/لاگ را می‌شود یک‌بار به‌صورت لایه‌ی مشترک دور همه‌ی Command/Queryها نوشت؛ دیگر لازم نیست توی هر اکشن جدا catch(Exception ex) بنویسی.
  • باگ فراموش‌شدن Include روی Genres در Movie — چون هر Query مسئول یک چیز خاص است، GetMovieListQuery می‌تواند دقیقاً کوئری‌ای بنویسد که لازم دارد، بدون رد شدن از یک Repository عمومیِ مشترک با بقیه‌ی عملیات‌ها.
  • الگوی Delete ناهماهنگ بین Repositoryها (Series درست، Movie/Genre ناقص) — هر Command مسئول چک کردن وجود entity قبل از حذف خودش می‌شود، و همه جا از یک الگوی یکسان پیروی می‌کند.

04نسخه‌ی سبک در مقابل نسخه‌ی کامل

نسخه‌ی سبک پیشنهاد ما

همان یک دیتابیس، همان Entityها؛ فقط Command/Query/Handler جایگزین متدهای Repository و کد داخل کنترلر می‌شوند. این چیزی‌ست که اغلب پروژه‌های واقعی وقتی می‌گویند «CQRS داریم» منظورشان است.

نسخه‌ی کامل

دیتابیس جدا برای خواندن و نوشتن، به‌علاوه‌ی Event Sourcing. برای سیستم‌های خیلی بزرگ با بار خواندن/نوشتن نامتقارن مناسب است — برای یک IMDB Clone قطعاً overkill است.

05هزینه‌اش چیست؟

هر عملیات ساده (مثلاً گرفتن یک ژانر با آی‌دی) الان یک کلاس Query به‌علاوه‌ی یک کلاس Handler می‌خواهد، به‌جای یک متد — یعنی فایل بیشتر و boilerplate بیشتر. در ازایش: تست‌پذیری خیلی بهتر چون هر Handler جدا تست می‌شود، جداسازی مسئولیت واضح، و امکان اضافه کردن رفتار مشترک بدون کثیف کردن کنترلر.

06نقشه‌ی راه Migration

  1. افزودن زیرساخت دیسپچرساخت اینترفیس‌های ICommand/IQuery، ICommandHandler/IQueryHandler، و یک IDispatcher ساده روی DI.
  2. Genreساده‌ترین Entity، از قبل تست دارد — اینجا الگو جا می‌افتد.
  3. Movieهمزمان باگ Genres/Include فیکس می‌شود چون Query از صفر نوشته می‌شود.
  4. Seriesچون Delete‌اش از قبل درست است، فقط شکلش عوض می‌شود.
  5. بقیه‌ی ماژول‌هاPerson، Cast، Rate، Comment، Episode، Season.
  6. Account / Authبررسی می‌شود که به همین شکل بماند یا به Command تبدیل شود.
